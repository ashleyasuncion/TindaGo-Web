2. Codebase Architecture & Payment Flow Tracing

The TindaGo system utilizes a hybrid architecture connecting the Android native app (Kotlin/Jetpack Compose) and the Web Customer Portal (HTML/JS) to Supabase (PostgreSQL database + Edge Functions) and PayMongo's payment gateway.

A. Android Mobile App POS Flow

  • Initiation: In CheckoutScreen.kt, the store owner builds a cart and selects GCash as the payment method (setSalePayment("gcash")).
  • Transaction Generation: Upon completion, a single clock read generates a synchronized posTransactionId (epoch millis), formatted into a sale reference string SALE-<millis>.
  • Local Record: The app optimistically records the sale locally into Room via AppViewModel.completeSale(...).
  • PayMongo Gateway Call: The app invokes openGcashCheckoutSession(), which performs an HTTP POST request to the Supabase Edge Function create-pos-payment.
  • Edge Function Action: create-pos-payment/index.ts talks to PayMongo's API (/v1/checkout_sessions) with line items and metadata. PayMongo returns a Checkout Session containing both a checkout_url and a qr_code_image_url.
  • UI Presentation: The Android app captures both URLs, displays an on-screen QR code overlay (GcashQrOverlay) for customer scanning, and starts polling the pos-status Edge Function every 2 seconds.

B. Web Customer Pre-Order Flow

  • Initiation: Customers browsing the web pre-order portal (preorder/app.js) add items to their cart and select GCash.
  • Session Creation: The frontend calls the Supabase Edge Function create-preorder-session, passing totalAmount, tempId, storeUid, and line items.
  • Redirect: The Edge Function returns a PayMongo checkoutUrl, and the browser redirects the customer via window.location.href = result.checkoutUrl.
  • Confirmation & Success: Upon payment completion on PayMongo's hosted page, PayMongo fires a webhook and redirects the customer to preorder/success.html, which polls preorder-status to confirm the DB update.

3. Investigation of the "GCash Transaction Failed" Error

When the Android app or web interface displays "GCash transaction failed. Try again.", it stems from the catch block surrounding the network call to the Supabase Edge Function:

catch (e: Exception) {
    Log.e("openGcashCheckoutSession", "Edge Function error: ${e.message}")
    toast("payGcashFailed".t(lang))
    return JSONObject()
}

Based on our codebase trace and Edge Function error handling, this failure can be triggered by:

  • Network Connectivity: Loss of internet connection on the tablet/phone while attempting to reach supabase.co/functions/v1/create-pos-payment.
  • PayMongo API Rejections: PayMongo rejecting the request due to missing headers, invalid amounts, or missing required attributes (e.g., historical issues with required currency: "PHP" on line items).
  • Missing Environment Secrets: If PAYMONGO_SECRET_KEY is not properly configured in the Supabase project vault, the Edge Function throws an unhandled error resulting in HTTP 500.
  • JWT / Authorization mismatch: If Edge Functions have verify_jwt = true in config.toml but requests are sent without valid Authorization headers. (Note: Current configuration correctly sets verify_jwt = false for payment functions).

4. PayMongo Integration Capabilities & Device Behavior

Comparing our implementation against standard PayMongo and e-wallet behaviors:

Same-Device Mobile Flow

When opened on a smartphone browser, PayMongo's hosted checkout page detects GCash and provides a direct button/deeplink to launch the native GCash app with pre-filled amount and recipient details.

Cross-Device / Tablet POS Flow

When a store owner uses a tablet or desktop POS, displaying PayMongo's generated qr_code_image_url on screen allows customers to scan the dynamic QR code directly using their own mobile GCash app.

5. Webhooks & State Synchronization

Automated payment confirmation relies entirely on server-to-server webhook delivery from PayMongo to the Supabase Edge Function paymongo-webhook/index.ts.

  • HMAC-SHA256 Security: Incoming webhooks are cryptographically verified using the webhook-signature header and timing-safe comparison.
  • Event Routing: Handles checkout.session.payment.paid (updates pre-orders from pending to preparing / paid) and payment.paid.
  • Transaction ID Matching: Ensures POS sales matching SALE-<millis> correctly update specific_sales.payment_method = 'gcash' by extracting the epoch timestamp and querying transaction_id.

7. Android POS Flow: Detailed Trace

Based on Explore Agent Results, the GCash POS flow in Android CheckoutScreen.kt operates as follows:

  1. User selects GCash (Step 3): Taps the GCash payment chip. Invokes viewModel.setSalePayment("gcash"), updating _salePayment StateFlow to "gcash".
  2. Completion (Step 5): On "Complete Sale" tap, the flow generates a single posTransactionId = System.currentTimeMillis() and builds saleReference = "SALE-${posTransactionId}".
  3. Local Persistence: Calls viewModel.completeSale(..., transactionId = posTransactionId), which creates SpecificSale entities in Room with paymentMethod = "gcash" (from _salePayment.value).
  4. Edge Function Call: Launches openGcashCheckoutSession(cartTotal, posSaleReference) in Dispatchers.IO coroutine. POSTs {totalAmount, saleReference} to create-pos-payment Edge Function.
  5. Response Handling: Parses JSON response. Extracts checkoutUrl and qrUrl. Sets showGcashQr = true to trigger the QR overlay.
  6. QR Overlay UI: Composables (GcashQrOverlay):
    • Loads QR PNG from qrUrl using BitmapFactory off main thread (HTTP GET + decodeStream).
    • Displays QR image centered. Shows status text: gcashQrWaiting, gcashQrPollError, or gcashDone.
    • Polls pos-status Edge Function every 2 seconds with the transactionId. Checks if payment_method === 'gcash'.
    • Auto-dismisses on payment confirmation (green check), then shows gcashDone toast and calls onPaid().
    • Fallback "Open checkout in browser" button uses checkoutUrl if QR fails.

8. Error Points & Logging Sources

The "GCash transaction failed" message originates from the payGcashFailed localization string, invoked in these specific error scenarios:

  • CheckoutScreen.kt:367 (Edge Function Call): When the POST to create-pos-payment fails (network error, 500 response). Logs: Log.e("openGcashCheckoutSession", "Edge Function error: ${e.message}")
  • CheckoutScreen.kt:457 (Empty qrUrl): If the PayMongo response has an empty qrUrl (though our Edge Function populates it from qr_code_image_url).
  • CheckoutScreen.kt:1212 (Browser Fallback): If failing to launch the browser intent (rare device-specific issue).
  • GcashQrOverlay.kt:1618-1619 (QR Load Failure): Network timeout or 404 when downloading the QR image.
